Cómo conectar Informix IBM a SAP Datasphere con una conexión Generic JDBC

Informix no aparece en la lista de conectores de Datasphere, y eso hace pensar que no se puede. Sí se puede: la ruta pasa por una conexión Generic JDBC apoyada en el Data Provisioning Agent. Esta es la preparación completa, incluida la dependencia que no sale en ninguna guía oficial y que bota la conexión al primer intento.

Por qué no hay un conector de Informix

Informix (IBM / HCL) no tiene un conector nativo en SAP Datasphere. La conexión se hace con el tipo Generic JDBC, que no corre en la nube: se ejecuta sobre el adaptador CamelJdbcAdapter del Data Provisioning Agent (DP Agent), un componente que se instala on-premise, del lado de usted.

Eso cambia el orden de las cosas. Antes de tocar Datasphere hay que tener un servidor con el DP Agent instalado, con red hacia el servidor Informix y con el driver JDBC de Informix copiado a mano. Mientras no haya un agente seleccionado, la función Tablas remotas de la conexión aparece como Deshabilitado — y ese es el síntoma que hace creer que la conexión quedó mal, cuando en realidad falta el agente.

Lo que hay que pedir antes de empezar

Casi todo el tiempo perdido en este tipo de conexión es tiempo esperando un dato que nadie pidió a tiempo. Vale la pena pedir todo de una vez:

A quiénQué
Admin de Informix Host/IP y puerto del listener (onsoctcp); nombre de la base de datos; nombre de la instancia INFORMIXSERVER (archivo sqlhosts); usuario de lectura (CONNECT + SELECT); locale de la base (DB_LOCALE) si hay tildes o eñes; versión de Informix.
Infraestructura / redes Que el servidor del DP Agent llegue al host y puerto de Informix, con el firewall abierto.

La prueba de red se hace desde el servidor del agente, no desde su equipo:

Test-NetConnection -ComputerName <IPInformixDatabase> -Port <PortDB>

Debe devolver TcpTestSucceeded : True. Si eso falla, no siga: todo lo demás va a fallar después y con mensajes mucho menos claros.

El driver JDBC y la dependencia que nadie menciona

SAP no entrega el driver. Hay que bajarlo de IBM/HCL o de Maven Central. Y aquí está el detalle que cuesta una tarde: los drivers 4.50.x dependen de la librería bson (la de MongoDB), que tiene su propia numeración. No existe un "bson 4.50". La versión que declaran los drivers 4.50 es bson 3.8.0.

Tip

En la página del driver en mvnrepository, la sección Compile Dependencies muestra la versión exacta de bson que pide esa versión del driver. Si falta el bson, el error típico es ClassNotFoundException: org.bson.BSONObject.

Preparar el DP Agent

  1. Instalar el DP Agent y registrarlo en Datasphere: Configuración del sistema → Integración de datos → Agentes on-premise.
  2. En <DPAgent_root>/camel/adapters.xml, verificar la entrada <Adapter type="CamelJdbcAdapter" ...>. La documentación de SDI indica descomentarla; en versiones recientes del agente ya viene activa. Debe existir una sola entrada, sin bloques viejos ni duplicados.
  3. Copiar jdbc-4.50.x.jar y bson-3.8.0.jar en <DPAgent_root>/camel/lib/. En Windows la raíz suele ser C:\usr\sap\dataprovagent\; en Linux, /usr/sap/dataprovagent/.
  4. Reiniciar el DP Agent.
  5. En Datasphere, sobre el agente, habilitar CamelJdbcAdapter y confirmar que el agente queda Conectado. Si se modificó adapters.xml, deshabilitar y volver a habilitar el adaptador para reregistrarlo.

La carpeta debe quedar así:

camel/lib/
  |-- jdbc-4.50.x.jar
  `-- bson-3.8.0.jar

Crear la conexión en Datasphere

En el espacio: Conexiones → Crear → Generic JDBC (JDBC genérico).

CampoValor
Clase de controlador JDBCcom.informix.jdbc.IfxDriver
URL JDBCjdbc:informix-sqli://<host>:<puerto>/<base_datos>:INFORMIXSERVER=<instancia>
Nombre de usuario / ContraseñaUsuario de lectura entregado por el admin de Informix
Agente de aprovisionamiento de datosEl DP Agent donde se habilitó CamelJdbcAdapter
Nombre de la empresa / técnicoNombre libre que identifique la conexión

Un ejemplo con valores ficticios:

jdbc:informix-sqli://10.0.0.25:9088/mi_base:INFORMIXSERVER=ol_informix1

Cuatro reglas sobre esa URL que conviene tener presentes:

  • INFORMIXSERVER es obligatorio y es el nombre de la instancia (el de sqlhosts), no el hostname. Es la confusión más común.
  • Los parámetros opcionales van separados por ; — por ejemplo DB_LOCALE y CLIENT_LOCALE. DELIMIDENT=Y conviene ponerlo siempre: sin él la tabla remota se crea pero no devuelve datos (ver más abajo).
  • No incluya la contraseña en la URL. Datasphere no la almacena cifrada.
  • La clase del driver se puede confirmar abriendo el jar como .zip y mirando META-INF/services/java.sql.Driver.

La tabla remota se crea pero no muestra los datos

Con la conexión ya validada y la tabla remota desplegada, la vista previa de los datos puede fallar con este mensaje:

Error interno: Falló la ejecución de DPAdapterResultSet::Fetch:Camel

No es red ni permisos: la conexión ya sirvió para leer el catálogo y crear la tabla remota. Lo que falla es el fetch de las filas. Datasphere genera el SQL con los nombres de tabla y de columna entre comillas dobles, y el driver de Informix solo interpreta las comillas dobles como identificadores delimitados cuando la sesión abre con DELIMIDENT=Y. Por defecto el parámetro va en N, así que esas comillas se leen como literales de texto y la consulta se cae del lado de Informix.

La solución es agregar ese parámetro al final de la URL JDBC de la conexión:

jdbc:informix-sqli://<host>:<puerto>/<base>:INFORMIXSERVER=<servidor>;DELIMIDENT=Y

Sobre el ejemplo anterior:

jdbc:informix-sqli://10.0.0.25:9088/mi_base:INFORMIXSERVER=ol_informix1;DELIMIDENT=Y
Tip

Conviene dejar DELIMIDENT=Y desde el primer momento, antes de crear tablas remotas: el error no aparece al validar la conexión ni al importar el catálogo, solo al leer los datos, y para entonces ya parece un problema de otra cosa. Después de editar la URL, guarde la conexión y vuelva a probar la vista previa; si la tabla remota sigue fallando, elimínela y vuelva a desplegarla.

Cuando falla: leer los logs del agente

Los logs del agente están en <DPAgent_root>/log/ — sobre todo framework.trc y framework_alert.trc. Para más detalle, se sube el nivel de trazas a ALL (KBA 2496051).

Limitaciones

Generic JDBC soporta tablas remotas: federación y snapshot o replicación programada desde la tabla remota. No soporta replicación en tiempo real, flujos de datos ni flujos de replicación.

Para volúmenes grandes conviene preferir snapshots programados en lugar de consultas federadas.

Dicho de otro modo: sirve muy bien para traer maestros y tablas transaccionales a un ritmo definido, y no sirve para un caso que exija latencia de segundos. Vale la pena dejarlo claro con el negocio antes de montar la conexión, no después.
